# Actual Tuplet placement before addition

A typed generator plan first returns the actual existing Tuplet object; this
precedes font access, scale validation and reading later null members. With none,
it selects THREE only when Math.rint(group size/3)==1, otherwise SIX, then infers
bounds on retained actual Chord caches and explicit immutable font resources.
Cached stem directions vote by count, negative wins equal counts, all zero uses
original-1. Bounds use integer rectangle union/center, height/10 margin and the
source direction-specific offset. Duplicate group entries count as separate
votes and in original size selection. Actual owner/clock storage is held.

Original fresh generateOneTuplet observes120 short/excess scenarios over all six
family values: lengths1..5, duplicate votes, up/down/equal/majority/all-zero, empty
and null groups. Native compares only the existing/pre-add placement boundary;
it does not claim native addition callbacks or generation/second pass yet. The
original360 vertex/relation callbacks and generated/removed state are losslessly
preserved for the next allocation dependency. Vertex registration occurs BEFORE
SIG attachment and TupletInter.added; normalization before that boundary is wrong.

Cache geometry is declared on existing real timed Chords solely to isolate source
placement; no physical Chord/Staff/Curve/Measure/Voice/Slot owner is reconstructed
from a report. The existing automatic Stem5px discrepancy remains a separate
unfinished recognition dependency. Family resources are supplied explicitly;
actual SheetStub family ownership is not inferred from a report or the calibrated
HEADS catalog. Ordinary fresh Tuplet/XML admission remains guarded.

Two native targets compare original shape/font dimension/bounds and held clocks,
physical Chord/Slot storage, actual Staff/Curve Arcs, old Voice slots/end/excess and
manual identities. A cold actual Stem with invalid width fails AFTER an earlier
